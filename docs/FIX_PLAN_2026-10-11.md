# Dashboard and website fix plan

Date: 2026-10-11
Scope: the dashboard checks and website checks raised on 2026-10-11, what causes each one, how to fix it, and other faults found while checking.

## How this was checked

- cdie.co.ke could not be reached from the build environment (its network policy blocks the host), so nothing here was measured on the live site.
- Instead the same code was built for production and measured in Chromium with Playwright: page loads, main-thread long tasks, frame rate, and how long a navbar click takes to change page.
- The build was run twice: once as it is, and once with Google Sheet credentials set, because production has the sheet connected and that changes how pages render.
- Frame rates come from software WebGL, so the absolute numbers are worse than on a real graphics card. The comparisons between them hold.
- Anything that depends on the live Google Sheet or the Vercel project settings is marked as needing confirmation.

## Summary of root causes

| Reported problem | Main cause found |
|---|---|
| Studio photo reorder not working | Read-modify-write against a cached read, and a "studio" row that can be written twice. Every later change goes to the first row while the site reads the last |
| Dashboard crashes to a black "reload" screen | Every save commits to `main` and redeploys the site, so open dashboard tabs ask a deployment that no longer exists. There is also no error boundary, and each page makes many uncached Google calls |
| Site load time and tab switching slower | With the sheet connected, About, Media, Programmes, MDI and Design Studio stop being static and render on every request, each making live Google Sheets calls |
| Design Studio lag and navbar lag | Both 3D rooms are built on page idle even if nobody opens them. The open room renders every frame, even off screen |
| Calendar misses announcements | Only dashboard entries reach the calendar. LinkedIn posts all go to "From our community" with no classification |

## Dashboard

### D1. LinkedIn link for an event's Read More

Fault
- The Events form has no link field (`lib/admin/collections.ts`). `getCalendarEvents` in `lib/events.ts` drops any link for dashboard events, so their cards show "CDIE event" instead of Read More.

Fix
- Add `{ name: "link", label: "LinkedIn post link", type: "url" }` to the events and activities collections.
- Pass `link: item.link` through in `lib/events.ts`, and show it in `ItemPreview`.
- Accept only `https://www.linkedin.com/` links (and optionally `lnkd.in`), the same check the LinkedIn helpers already use.
- Effect: `scripts/sync-linkedin.mjs` already picks up cms events that have a LinkedIn link and no image, so these events also get the post's photograph automatically.

Size: small.

### D2. Reordering Design Studio photographs

What the snapshot shows
- Reorders do reach the sheet: electronics was reordered on 2026-10-06 and is in `content/cms-snapshot.json`. The fault is intermittent, not total.

Faults in `app/admin/studio-actions.ts` and `lib/admin/store.ts`
- `photosOf()` and `saveStudioPhotos()` read through `load()`, which is cached for 300 seconds. A swap is computed from whatever list the cache holds. A stale list writes an old order back, which looks like the click did nothing or undid an earlier move.
- `saveStudioPhotos` decides whether to append or update from that same cached read. Two quick clicks, or one stale read, append a second row for the same capability.
- After that, `updateRow` always updates the first matching row, while `studioPhotoOverrides()` keeps the last row it reads. Every later reorder lands in a row the site ignores. This matches "reorder not working" in one area while it works in another.
- The arrow buttons are separate forms with no pending state, so several clicks fire several overlapping read-modify-write actions.
- Every click also fires a GitHub dispatch, which commits a snapshot and redeploys the site (see D6).

Fix
- Do read-modify-write against an uncached read: a `loadFresh()` that bypasses the fetch cache, used by every server action that changes data.
- Make the studio write a real upsert. Delete every row for the capability, then write one. When reading, take the row with the latest `at`, so any existing duplicates resolve themselves.
- Replace the per-click swap with an ordered list the editor arranges (drag and drop, keeping the arrow buttons for keyboard use), saved in one action. Use `useOptimistic` and disable the controls while a save is pending.
- Debounce the GitHub dispatch (see D6).
- Check the live sheet's "studio" tab for duplicate capability rows and remove them once the fix is in.

Size: medium.

### D3. Edit staff (photograph, role, name)

Fault
- Staff can only be added or removed. Changing a role or photograph means deleting a record and adding it again.
- Staff that ship with the site (`content/about.ts`) can only be hidden.

Fix
- Add an Edit control to each card in `/admin/[collection]`. It opens the same `ItemForm`, pre-filled. Image fields keep the current file unless a new one is chosen.
- Dashboard records: a new `editItem` server action that calls the existing `updateItem` (store) after the same validation as `createItem`.
- Site records: add an "overrides" tab keyed `collection:key`, holding only the changed fields, merged over `content/about.ts` when the About page reads the team. This is the same pattern as the studio photo overrides, and the code record stays as it is.
- Build it for all collections at once (newsletters, events, cohorts), not only staff. The work is the same.

Size: medium.

### D4. Activity log: who signed in and what they changed

Fault
- Nothing records sign-ins or changes. `currentAdmin()` already knows the signed-in email, but no action writes it anywhere.
- Needs confirming: whether production has `ADMIN_AUTH=on`. While it is off there is no identity to log, and the README still records the 2026-09-22 "no login for now" decision.
- With the shared `ADMIN_PASSWORD`, anyone can sign in under any listed address, so the logged name is only as trustworthy as personal accounts make it.

Fix
- Add an "audit" tab (sheet) and an `audit()` helper in `lib/admin/audit.ts` with the fields at, who, action, collection, record id, record title and a short summary of what changed. Never include passwords or upload bytes.
- Call it from login (success and failure), logout, signup, createItem, editItem, deleteItem, hideItem, studio photo changes and sendIssue.
- Add a dashboard page `/admin/activity` listing the latest 200 entries, with a filter by person and section.
- Turn sign-in on in production (`ADMIN_AUTH=on`). Once each team member has a personal account, retire the shared password.

Size: medium.

### D5. Contact form emails: one click to reply

Faults
- In the dashboard, the sender's address is a `mailto:` link, and it only shows when sign-in is on. With sign-in off the panel holds the details back, so there is nothing to click.
- `mailto:` opens the computer's default mail program. On a machine with none set up, which is common for people who use Gmail or Outlook in the browser, the click does nothing.
- `EnquiryPanel` keys entries by `entry.at`. Two forms in the same millisecond collide. This is rare but easy to fix.

Fix
- Beside each address, add a Reply in Gmail link and a Reply in Outlook link, each opening a new message with the address, a "Re: Website enquiry" subject and the original message quoted. Add a Copy address button too.
  - Gmail: `https://mail.google.com/mail/?view=cm&fs=1&to=…&su=…&body=…`
  - Outlook: `https://outlook.office.com/mail/deeplink/compose?to=…&subject=…&body=…`
- Check the delivered enquiry email sets reply-to as the enquirer, so Reply works straight from the inbox:
  - Resend already sets `reply_to`.
  - Web3Forms needs `replyto`.
  - The Apps Script path needs `replyTo` in `MailApp.sendEmail`.
- Depends on D4: turning sign-in on is what lets the addresses show.

Size: small.

### D6. Dashboard crashes to a black "reload" screen and feels slow

Causes, most likely first
- Deployment skew.
  - Every dashboard upload commits a file to `main` (`commitUpload`).
  - Every save fires `cms-updated`, which commits the snapshot.
  - The LinkedIn sync commits every three hours, and the CMS sync every hour.
  - The git log is mostly these commits, and each one is a production deploy.
  - A dashboard tab opened before a deploy then asks for page data and script chunks that the new deployment does not have. Next shows its full-screen "This page couldn't load, reload" error.
  - This explains why it happens "when clicking some pages", and more often right after saving.
- No error boundary.
  - There is no `error.tsx`, `global-error.tsx` or `loading.tsx` anywhere under `app/`.
  - Any thrown server error, such as a Sheets quota error from `updateRow`, `deleteRows` or `findAccount`, which are not caught, replaces the whole screen.
  - With no loading state, a slow page shows nothing until it finishes.
- Too many uncached Google calls.
  - Every `load()` call fetches the sheet's tab list with `cache: "no-store"`, then the values.
  - The overview calls `load()` about nine times per view (four collections times two, plus analytics), and `load()` is not wrapped in React `cache()`.
  - That is slow, and it uses up the Sheets read quota (60 reads per minute per user), which then produces the errors above.
- Large server bundle.
  - The build warns that `process.cwd()` in `lib/admin/store.ts` makes the whole project, including the 74 MB `public` folder, get traced into the server functions.
  - Bigger functions start slower.

Fix
- Turn on Vercel Skew Protection for the project, so open tabs keep talking to the deployment they loaded from.
- Stop committing uploads to git. Store them in Vercel Blob (or the sheet's Drive) and save only the URL. Upload then no longer causes a deploy.
- Debounce `notifyContentChanged`, so one batch of edits makes one snapshot commit, not one per click.
- Add `app/admin/(secure)/error.tsx` with a Try again button, a `global-error.tsx`, and `loading.tsx` skeletons for the dashboard pages.
- In `lib/admin/sheets.ts`, cache the tab list under the `cms` tag. Wrap `load()` in React `cache()` so one request reads the sheet once.
- Catch Sheets errors in every action and return a readable message instead of throwing.
- Scope the data directory path (`path.join(process.cwd(), ".data")` with the turbopackIgnore hint) so `public/` is not traced into functions.

Size: medium. Skew Protection on its own is a settings change and should stop most of the crashes on the day it is switched on.

## Website

### W1. Load time and tab switching got slower

Cause, confirmed in a build with sheet credentials set
- Production has the Google Sheet connected.
- Every Sheets read starts with an uncached call (the access token fetch and the tab list, both `cache: "no-store"`).
- A `no-store` fetch makes a page dynamic, so About, Media, Programmes and the MDI page are rendered on every request. Design Studio was already dynamic.
- Each request makes three or more round trips from Vercel to Google before any HTML is sent.
- A plain build without credentials shows those pages as static, which is why the slowdown arrived with the sheet and not before.

| Route | Without sheet | With sheet (production) |
|---|---|---|
| /about | static | rendered per request |
| /media | static, refresh every 10 min | rendered per request |
| /programmes | static, refresh every 10 min | rendered per request |
| /programmes/mdi | static | rendered per request |
| /design-studio | per request | per request |

Fix
- Public pages should read content through a cached function tagged `cms` (Next 16 `"use cache"` with `cacheTag("cms")`, or `unstable_cache`). They stay static or revalidate on a timer, and a dashboard save refreshes them at once through the `updateTag(CMS_TAG)` calls that already exist.
- Cache the tab list and keep the token request out of the render path.
- Design Studio: read `service` on the client (it already writes it with `history.replaceState`) so the route can be static too.
- Prefetching: navbar links are `next/link` and prefetch static routes. Once the pages are static again, tab switches come from the prefetch cache.

Size: medium. This is the change with the largest effect on speed.

### W2. Design Studio: slow loading, lag after visiting, navbar lag

What was measured, with the same code built for production
- Design Studio does 944 ms of main-thread long tasks at load, the worst being 738 ms. Other pages do nearly none.
  - Cause: `useStudio3DWarmup` builds both rooms (two WebGL renderers, two 2048-pixel shadow maps, all the procedurally generated geometry) as soon as the browser is idle, whether or not anyone opens the 3D view.
- Design Studio loads 1.37 MB of script against about 0.68 MB on other pages, three.js plus both models.
- With the room open, the scene renders every frame at up to twice the screen's pixel density with antialiasing and shadows, and keeps doing so after the room is scrolled out of view (no pause when off screen).
- With the tour running, a navbar click took about 3 seconds to change page, against about 0.35 seconds normally. That is the reported navbar lag.
- After leaving, the next page recovers its frame rate, so the scenes are cleaned up. However, `renderer.dispose()` is called without `forceContextLoss()`, so each visit leaves two WebGL contexts for the browser to reclaim later. Chrome caps live contexts at 16, and repeat visits push toward that cap.
- Bug: the "Explore in the room" button on a capability card changes the address to `?service=woodworking`, but the explorer stays on Design and CAD.
  - Cause: `StudioExplorer` keeps `initialId` in state and never follows a new one.
  - It also causes a needless round trip to the server.

How heavy, well-regarded sites run 3D without slowing the page
- Poster first. Show a still image or a short video, and load the 3D code only on intent (hover, click on "3D view") or when the canvas scrolls into view. Never at page idle.
- Render on demand. Draw a frame only when something changes (camera moving, damping settling, the tour, a selection), not 60 times a second while still.
- Pause when unseen. Stop the loop when the canvas is off screen (IntersectionObserver) or the tab is hidden (visibilitychange).
- One context. Use a single renderer and canvas, and swap which scene it draws, instead of two renderers.
- Adaptive quality.
  - Cap the pixel ratio at 1.5.
  - Drop resolution or shadows when frame time rises.
  - Make the static room's shadows render once (`shadowMap.autoUpdate = false`), or bake them into textures.
- Pre-built, compressed assets. Export the rooms once to glTF with Meshopt or Draco geometry and KTX2 textures, instead of generating the geometry in the visitor's browser on the main thread. Merge or instance repeated furniture to cut draw calls.
- Work off the main thread. Where supported, build and render in a Web Worker with OffscreenCanvas, so the page stays responsive while the room loads.
- Clean exit. Call `forceContextLoss()` after `dispose()`.

Plan, in order
1. Fix the "Explore in the room" selection bug (small).
2. Stop the idle warmup of both scenes. Prefetch only the code on hover of "3D view", and build on click (small).
3. Add the off-screen and hidden-tab pause, render on demand, a pixel ratio cap of 1.5 and one-time shadows, and call `forceContextLoss` on unmount (medium).
4. Merge the two renderers into one canvas that switches scenes (medium).
5. Export both rooms to compressed glTF and load them in place of runtime generation (larger, and needs the layout module as the source of positions, per `AGENTS.md`).

Steps 1 to 3 should remove the navbar lag and the load-time cost. Steps 4 and 5 are about smoothness on low-end phones.

### W3. LinkedIn announcements and events into the calendar automatically

Fault
- The team does not add events by hand.
- Every LinkedIn post goes to "From our community", including:
  - "Join us this Friday … Date: Friday 9 Oct, 4PM, Kahawa Sukari Football Turf"
  - the "Own What You Build" IP workshop
  - "The Catalyst Grant is still open … Rolling review"
- All three are in the current snapshot.

Plan
- Classify each post in `scripts/sync-linkedin.mjs`, which already runs every three hours and at build time, into one of these kinds:
  - event: has a date or time and a place or "join us", "register", "RSVP", "workshop", "session"
  - announcement: "applications open", "call for", "now open", "still open", "deadline", "rolling", "grant", "apply"
  - community: everything else
- Also treat a post that links to `linkedin.com/events/` as an event.
- Dates come only from the post itself:
  - an explicit date ("9 Oct", "Friday 9 Oct", "October 12")
  - a weekday ("this Friday") resolved against the post's own date
  - with no date in the text, the post's date, labelled Announcement rather than as an event date
- That keeps to the claim-safety rule: no date is invented, and each card links back to the post as its source.
- Write the classified items to a `calendar` array in `content/linkedin-snapshot.json`.
- `getCalendarEvents` merges them into the calendar. The Media carousel leaves them out, so a post shows in one place, not both.
- Give each post a dashboard override, "LinkedIn posts: show in calendar / show in community / hide", plus a date correction, stored as override rows, so a wrong guess is one click to fix and the fix survives the next sync.
- Cover it with tests: add `tests/linkedin-classify.test.mjs` with the posts above as fixtures (Friday match, Catalyst announcement, metalworking class as community).
- Optional later: if the rules miss too much, classify with the Claude API using structured output, on the sync only (eight posts every three hours, negligible cost). Keep the rules as the fallback.

Size: medium.

## Other faults found

- The design studio route is dynamic only because it reads `searchParams`. See W1.
- `EnquiryPanel` uses the timestamp as a React key (D5).
- No `error.tsx`, `loading.tsx` or `global-error.tsx` anywhere in the app, public site included (D6).
- `public/` is 74 MB and several originals are over 0.5 MB, `service-coworking-1.jpg` at 1.9 MB.
  - Pages that use `next/image` are resized on the fly, but `EventCard` and the dashboard cards use plain `<img>` and send the full file.
  - Fix: resize the originals to at most 2560 pixels wide, and use `next/image` on the calendar cards.
- The Lenis smooth-scroll loop and the GSAP ticker run every frame on every page. Lenis is already switched off for touch and reduced-motion users. On Design Studio it competes with the 3D loop for the same frames. Pause it while the room is open and being dragged.
- Sign-in is off by default (`ADMIN_AUTH`). Until it is on, anyone with the address can change the site, and D4 has no names to record.
